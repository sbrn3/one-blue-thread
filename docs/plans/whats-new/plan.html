Problem & Intent

Status, owner & next action

Approved by the owner 2026-10-07. Built on feat/whats-new (see PROGRESS.md). Next action: PR and merge, then the owner's spot-check on the dev client.

Outcome and constraints

An update currently arrives silently: the reader gets a new APK and has no way to learn what changed. After every update that changes something a reader can notice, the app should say so once, quietly, and keep every past note somewhere findable.

Constraints:

  • Scripture-first voice (docs/CONTEXT.md). Notes are brief operational prose. No devotional framing, and no marketing tone inside the app.
  • Never blocks reading. The card is never a modal and never covers Scripture.
  • Offline and private. Notes are bundled in the binary: no network, no events, no analytics.
  • §13.6 hard rules untouched: no events rows, no migration, no PRNG.

Scope and non-goals

In scope:

  • A bundled, ordered list of release notes.
  • A dismissible card in the flow showing only the notes the reader hasn't seen.
  • A permanent "What's new" row under Knot › More › About.
  • Fresh installs that don't see a card.
  • A standing release rule in AGENTS.md.

Non-goals:

  • Bumping the native versionName, which is stuck at 1.0.0.
  • Over-the-air update delivery.
  • Telling the reader an update is available.
  • Release notes on GitHub Releases, which are already auto-generated there.

Dependencies and unresolved gates

  • No product gates are open. The owner settled all three in chat (quiet card, history in the knot, Claude drafts the notes).
  • Commit/push/PR/merge: not yet authorised for this plan. Plan approval alone doesn't cover it.
  • Another session's uncommitted work: thread/ has uncommitted changes in src/knot/TranslationSection.tsx and docs/plans/translation-key-guide/. The worktree must start from origin/main and must not touch them.

Evidence and decisions

  • Seen-state: follows the existing one-time flag pattern, meta key study_hint_seen (src/flow/Flow.tsx ~L292) and year_review_shown (~L119). The meta table already exists, so no migration is needed.
  • Reset: src/reset/index.ts RESET_TABLES clears meta, so an unravel returns the reader to "fresh install" behaviour automatically.
  • Fresh install: src/onboarding/OnboardingFlow.tsx ~L73 sets onboarded, and the seen marker is set beside it. An onboarded reader with no marker therefore upgraded from a build before this feature.
  • Release id: the native version is always 1.0.0 and BUILD_SHA changes every build. Notes are therefore keyed by the release tag (v0.10.0…), and the bundled list is the only version source the card needs.
  • Copy inventory: test/brand-voice.test.ts requires every new copy-bearing .tsx to be classified in docs/brand-voice-inventory.json.
  • Owner decisions, 2026-10-07: quiet card in the flow (not a sheet or modal); history under Knot › More › About; Claude drafts each release's 1–3 lines and the owner edits them in review.

Documentation effects

  • AGENTS.md: the release paragraph (~L37) gains the rule "a user-facing tag ships a What's new entry".
  • docs/brand-voice-inventory.json: two new entries.
  • STATUS.md, ROADMAP.md and docs/plans/README.md: updated together when the plan becomes active.

Requirements (confirmed)

User stories

  1. As a reader who has just installed an update with a note, I want a short "New in this update" card above the day's reading, so that I know what changed.
  2. As a reader who skipped one or more updates, I want the card to list every note I haven't seen, newest first, so that nothing is lost.
  3. As a reader, I want "Got it" to dismiss the card for good, so that it never returns for the same notes.
  4. As a reader, I want the card never to cover or delay Scripture, so that the app stays a quiet place to read.
  5. As a new reader finishing onboarding, I want no What's new card, so that my first day isn't about changes I never saw.
  6. As a reader upgrading from a build before this feature, I want to see only the newest note, so that I'm not shown a backlog.
  7. As a reader who has unravelled (account reset), I want to be treated as new, so that the card doesn't appear after re-onboarding.
  8. As a reader, I want every past note under Knot › More › About › What's new, newest first, so that I can re-read a note I dismissed.
  9. As a reader using a screen reader, I want the card announced politely, with a labelled 44pt dismiss button, so that it's as reachable as the study hint.
  10. As a reader with large system text, I want the card's lines to wrap without clipping.
  11. As a reader on an update with no new note (fixes only), I want no card.
  12. As a reader, I want the What's new card and the study hint never to show together, so that the top of the page holds at most one card. What's new takes priority, and the study hint shows on a later sitting.
  13. As the owner, I want a test to fail if a release entry is malformed (duplicate id, not ordered newest first, empty or more than 3 lines, a line over 120 characters), so that a bad entry can't ship.

Out of Scope

  • Matching the note to the installed native version. The bundled list is the source of truth, and a dev build simply shows whatever is bundled.
  • Notes for releases before this feature (v0.6–v0.9). The first entry is the release that ships this. Backfilling would only be seen in the knot history, and the owner can add old entries later.
  • Event-log rows for card views or dismissals. This would add data and analytics surface for no research question.
  • Animation. The study hint has none, and this card matches it.

Testing Decisions

  • The seam is a pure function, unseenReleases(releases, seenId), in src/whatsNew/index.ts. Cases:
    • seenId null → newest only (story 6);
    • seenId equal to the newest → none (stories 3 and 11);
    • seenId older → every newer entry, newest first (story 2);
    • an unknown seenId → newest only;
    • an empty list → none.
  • Data invariants on the bundled RELEASES (story 13): unique ids, vX.Y.Z format, strictly descending by semver, 1–3 lines, each line 120 characters or less.
  • Closest prior art: test/year-review.test.ts (a one-shot meta flag decision) and pure-module tests like test/dismissalReadiness.test.ts.
  • test/brand-voice.test.ts already guards that the new .tsx files are classified.
  • Not unit-tested: component rendering. The suite has no RN renderer, a known gap noted in STATUS.md. Placement in Flow and the knot row are checked on the dev client.
