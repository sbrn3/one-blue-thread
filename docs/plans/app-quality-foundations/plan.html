Problem & Intent

Status, owner & next action

Status: shipped. All seven slices merged to main in order (#11–#17) and tagged v0.5.0. Trigger: the user asked to plan every audit recommendation except translation switching, explicitly endorsed a first-class local diagnostics and Support section, requested a different PR for every slice, and specified that loading must visibly use weft and retain the app’s wavy tension; the active-weft loading direction was confirmed 2026-09-05. Next action: run the device-verification pass this plan could not perform in this environment — bundled OTF font assets (none exist yet), the TalkBack/VoiceOver/Switch Control/200% text matrix, real launch timing, and an on-device exercise of the real expo-file-system recovery-snapshot move/rotation calls. Each ticket below records its own exact gaps.

Outcome and constraints

Thread should retain its calm, single-flow ritual while becoming honest about recovery, visually faithful to its declared type system, operable with touch/keyboard/Switch Control/large text, explicit during loading and failure, and easier to navigate without becoming a conventional settings app. Privacy remains on-device and single-user; no account, analytics, cloud provider, networked partner path, new event type, migration, or PRNG change.

Scope and non-goals

In scope: packaged fonts; portrait-safe layouts; visible session loading/error/retry without state drift; a repository-wide 44pt interaction audit; accessible sealing with a two-tap alternative and disabled explanation; truly terminal post-seal dismissal; honest, restorable automatic recovery snapshots plus manual external export confirmation and surfaced failures; reset/rollback cleanup; Direction A quiet-accordion knot; virtualized/searchable recorded reading history; a first-class local Support disclosure with bounded, redacted issue context and previewable diagnostics; reduced-motion modal behavior; study discovery hint; remaining hard-coded color repair; accurate backup copy and supporting docs. Explicitly parked: the separate knot-translation-switch plan and every translation setting/provider/key/fallback change.

Also out of scope: automatic Google Drive/iCloud integration (requires provider/account/background-policy decisions); changing the backup crypto format; a new navigation framework; theme switching; landscape support (the existing portrait lock remains); changing loom geometry; changing the experiment engine, notification schedule, 4 AM boundary, partner hand-off, or reset semantics beyond deleting the new snapshot artifacts.

Dependencies and resolved gates

Implementation uses reviewed static OTF font files and their OFL notices, expo-font ~57.0.3, and the existing react-native-safe-area-context ~5.7.0. Load explicit static face names at runtime with useFonts on native and web; do not use variable fonts or mix runtime loading with the native-only config-plugin route. Every StyleSheet migrates from family-plus-weight composition to a semantic face token, with legible platform fallback if font loading reports an error. A root provider supplies insets, while each screen/modal must consume them; provider presence alone does not inset content. Paths.document is persistent app document storage, while Paths.cache is purgeable. Sources: Expo Font, Expo font guide, Expo safe areas, Expo FileSystem API family used by SDK 57. No unresolved product decision remains: the user selected Direction A, endorsed local Support, and this plan labels on-device snapshots separately from externally saved backups.

Evidence and decisions

The audit is grounded in src/ui/tokens.ts, all screen StyleSheets, App.tsx, src/state/session.ts, src/backup/*, test/backup.test.ts, test/session.test.ts, the canonical docs/index.html, product spec §§04/05/13.4/16.9/19, and the Loom decisions in JOURNAL.md. Direction A was selected from the three-option mockup, and the user refined the loading direction into the progressively woven page.

Requirements

User stories

  1. As a reader, I want the shipped app to render Schibsted Grotesk, Newsreader, and JetBrains Mono as designed, so the native experience matches Thread’s visual identity.
  2. As a reader whose device cannot load a bundled font, I want legible system text and a locally logged diagnostic rather than a blank app.
  3. As a reader opening Thread, I want Thread’s familiar wavy weft to pass visibly across slack warp—alternating direction row by row—while completed rows tighten into cloth behind the fell line, so startup shows weaving rather than merely revealing a finished graphic.
  4. As a reader whose database, services, fonts, or portion fail to initialize—or remain pending too long—I want a plain explanation, Retry action, and bounded copyable startup details, so no startup route strands me on blank paper.
  5. As a reader on a notched phone, tablet, or device with a home indicator, I want content and controls inside safe areas.
  6. As a reader using touch, I want every actionable control to expose at least a 44×44pt target without overlapping neighbouring targets.
  7. As a reader using 200% OS text, I want actions to wrap or stack and every screen—including completion and the knot—to remain scrollable without clipped text.
  8. As a reader using reduced motion, I want knot and history modals to open without slide animation while direct-manipulation progress remains accurate.
  9. As a reader who has not reached the completion floor, I want the seal to explain what remains instead of appearing mysteriously dimmed.
  10. As a keyboard or Switch Control reader in the hold arm, I want a visible two-step tap alternative, so sealing does not require a long-press gesture.
  11. As a reader in the tap experiment arm or using a screen reader/reduced motion, I want the existing direct Seal button behavior preserved.
  12. As a reader after sealing, I want every due questionnaire, annual review, report, book-end choice, and promotion presented before the terminal instruction.
  13. As a reader, I want “Now close the app” to be the final rendered element, so following the instruction cannot hide unfinished work below it.
  14. As a new reader, I want the knot labelled and at least 44pt while remaining visually quiet, so the app’s only persistent control is discoverable.
  15. As a reader opening the knot, I want today’s compact weave summary followed by grouped disclosure sections, so infrequent tools do not create a very long undifferentiated sheet.
  16. As a reader, I want the cue open by default and its current sentence visible in the collapsed summary, because it is the app’s primary setting.
  17. As a reader with a failed or missing external backup, I want Backup opened or marked for attention without alarmist copy.
  18. As a reader, I want weekly automatic files described as on-device recovery snapshots, so I do not mistake them for protection from a lost phone.
  19. As a reader, I want automatic recovery snapshots stored under persistent document storage, not purgeable cache, with the newest successful time visible.
  20. As a reader exporting manually, I want to confirm whether I saved the file outside the phone before Thread records an external-backup date.
  21. As a reader who cancels sharing, I want Thread to continue showing that no external backup is confirmed.
  22. As a reader whose weekly snapshot fails, I want a visible local status and a retry/export route in the knot; the failure must also remain in local diagnostics.
  23. As a reader using encrypted exports, I want passphrase, encryption, wrong-passphrase, and restore behavior unchanged.
  24. As a long-term reader, I want to load earlier history beyond the latest 100 records until any recorded sealed portion is reachable.
  25. As a reader, I want history grouped by book/date and searchable by canonical book name, with loading, empty, no-result, and retry states.
  26. As a first-time study user, I want one restrained hint explaining that verses open study context and can be remembered, so the feature does not depend on guessing.
  27. As a returning reader, I want that hint to remain dismissed locally and never become an event or experimental signal.
  28. As a reader, I want remembered verse tint, selected labels, and modal scrims sourced from design tokens rather than legacy hard-coded colors.
  29. As the silent lab, I want all existing event rows, 4 AM dates, phase/reconcile behavior, year-one experiments, and post-day-366 adaptive behavior byte-for-byte unaffected.
  30. As an offline reader, I want WEB reading, Tyndale study, history, recovery snapshots, and every new UI state to work without a network connection.
  31. As a reader returning after missed days, I want the bolt’s bare warp/set marks and lapse behavior unchanged by the new knot structure.
  32. As a reader who needs help, I want a clearly named Support disclosure showing recent local issue and amendment context plus a Copy diagnostics action, so I can understand and share useful information deliberately.
  33. As a privacy-conscious reader, I want Support to state that diagnostics remain on-device until I copy/share them, so the absence of telemetry is visible rather than merely implicit.
  34. As a reader recovering this installation, I want to inspect and restore the current or previous on-device snapshot, including encrypted snapshots, with the existing destructive-restore confirmation.
  35. As a reader resetting Thread, I want every recovery snapshot and temporary share artifact deleted before the encryption key and database are cleared, so sensitive or unusable files are not orphaned.
  36. As a reader opening a recorded portion, I want its viewer to show loading, failure, and Retry states without dismissing my history context.
  37. As a reader copying diagnostics, I want to preview a bounded, sanitized payload that cannot contain verse text, cues, reflections, partner details, API keys, file tokens, email addresses, or phone numbers.
  38. As a reader, I want calm and predictable backup attention: snapshot attention after a foreground attempt has never succeeded or currently fails; external-backup attention after a seven-day new-user grace period when never confirmed, or after 90 days without reconfirmation.

Out of Scope

  • Automatic third-party cloud upload or background execution. Thread remains provider-free; manual OS sharing is the external-backup boundary.

  • Component-rendering tests or a new test library; repository policy keeps Vitest on pure logic/fakes.
  • A finished-book shelf, cross-book analytics, theme switcher, bottom navigation, or router.

Direction

Intent: extend the Loom rather than redesign it—quiet, legible, and deliberate. Hygiene: exact current palette paper #F4F1E9, ink #1A1A17, thread #2E3A8C, warp #8F8779, madder #B5482F, dyeSoft #E7E9F4, ink60 #5B584F, ink40 #726D5C, ink15 #E0DACB. Details: launch begins with faint, visibly slack warp generated by the existing warpPath geometry. The existing wavy weftPath for row 0 draws from left to right; row 1 draws right to left; subsequent rows alternate likewise. A row is not cloth until its weft pass completes: then its taut warp and alternating ridesOver segments appear and the fell line steps to that row. The lower unwoven area remains loose and open, so tension—not a rigid grid or a masked finished image—carries the motion. Status copy appears only after 400ms; the finite sequence takes about 13 seconds and then rests rather than looping or implying a percentage; success accelerates the remaining row windows over at most 180ms before the cloth dissolves into the reading; prolonged loading changes the copy and reveals Retry/Copy startup details; reduced motion renders the completed cloth immediately; decorative SVG is hidden from accessibility; cue is open by default; backup opens only when attention is needed; disclosures announce expanded state; pressed state uses subtle dyeSoft/opacity; focus order follows visual order; sheet and completion remain scrollable; reduced-motion sheets use none; long copy wraps; loading/error/empty/retry are explicit.

src/ui/LaunchWeave.tsx — NEW
Build a decorative full-page relative of Cloth using existing `geometry`, `warpPath`, `weftPath`, `weftPoints`, `polylineLength`, and `ridesOver`—do not invent separate loading geometry, and do not raise `MAX_ROW_PITCH`/`MAX_SETT` or otherwise edit `loom.ts`. `rowPlan` clamps and never stretches, so `geometry(screenW, screenH, 11, Array(21).fill(true))` returns `sx`/`sy` of 16 and a 180×340 `clothSize`; scale that box uniformly by 1.625 into a ≈292×552 field, which reproduces the approved mockup's 26px pitch exactly, and divide every `strokeWidth` by 1.625 (2.5 → 1.54) so line weight still matches the app's cloth. Do not instead pass 41 sealed days to make the cloth fill the screen at pitch 16 — that doubles both the density and the pace. Slack and taut warp are two geometries over the same box: `sealed` all-false puts `dist` at 4.5 everywhere (slack), all-true puts it at 0 (taut), while sett, pitch and `clothSize` are identical between them, so the two path sets register exactly. Paint the all-false warp for the full field, extending the first and last spans off both screen edges with a negative `fromRow` and a beyond-last `toRow` (`warpPath` does unclamped arithmetic on row indices). Give each wavy weft row its own Reanimated strokeDashoffset window, like Unravel in reverse: even rows draw left-to-right and odd rows reverse the generated points to draw right-to-left. Only after a row's weft window completes may its taut warp/alternating warp-over segments reveal and the fell line step down. This must visibly insert weft, not clip-reveal prepainted cloth. Run one finite ~13s sequence (21 rows, one pass every 600ms over 520ms) from a fixed synthetic row/column pattern; never derive it from personal reading data, loop it, or label it as percent progress. Delay `Preparing today’s reading…` until 400ms. On success, compress remaining row windows into at most 180ms and dissolve the cloth into content. At 14s — after the weave completes, never during it — hold the completed weave, announce `This is taking longer than expected`, and reveal 44pt Retry / Copy startup details. With reduced motion, show completed static cloth and status immediately. Mark SVG inaccessible and expose one polite live-region status.
src/ui/FeedbackState.tsx — NEW
Presentational ErrorState and non-launch loading states using tokens. ErrorState accepts calm allowlisted message/code + onRetry + optional onCopyDetails. Controls expose accessible role/state and a minimum 44pt target; no database/service import and no raw error text.
src/state/session.ts — MODIFY (SessionState.load)

Stage first-book/current-portion defaults in memory, call loadPortion, and commit state/meta/book_start only after success. On rejection, preserve prior ready data and write no meta/event. Ignore completion from any older generation so overlapping Retry calls are latest-wins.
