Problem & Intent

Status, owner & next action

Implemented; release verification complete. The reader approved the plan and its five slices. Owner: Thread implementation session. Next action: deploy v0.3.0 and confirm the Android release workflow.

Outcome and constraints

Readers should encounter useful study help without turning Scripture into a link farm: a few exact dictionary terms are quietly signposted; tapping elsewhere opens a verse-context sheet with relevant Tyndale notes and deliberate remembering controls. All content and search work offline, no reading/search telemetry leaves the device, and existing deterministic memory/event behavior remains intact.

Scope and non-goals

Scope: Tyndale Open Study Notes, book introductions/summaries, theme notes and profiles; dictionary text and local search; inline cues; verse context; same-chapter passage selection; attribution. Non-goals: Gospel Coalition/Crossway text, Tyndale maps/charts/pictures/textboxes in v1, cross-chapter ranges, cloud search, accounts, recommendations, or new experiments.

Dependencies and unresolved gates

Start with two parallel proofs: a Philippians end-to-end resource/context tracer and the independent range-memory interaction. Corpus expansion follows only if the tracer meets these provisional budgets on the baseline Android device: release APK increase ≤18 MB, active-chapter study load ≤150 ms, cold-start regression ≤100 ms, and incremental heap after one note plus one dictionary article ≤12 MB. No product decision remains. Engineering gates: the transformed data must pass CC BY-SA checks and all 66 source book identifiers must map to Thread IDs. A budget miss pauses expansion for a documented storage decision rather than silently raising the limit.

Evidence and decisions

src/flow/ScriptureZone.tsx owns verse presses; src/flow/Flow.tsx::handleMarkVerse currently creates one-verse candidates; src/memory/memory.ts::PassageRef already accepts verseStart/verseEnd, so no schema migration is needed; src/knot/Knot.tsx is the persistent revisit surface; src/services/index.ts composes app-lifetime providers. The official archives contain verse-range XML notes and 6,000+ dictionary articles. The latest user statement approves inline dictionary cues + a general verse sheet + explicit single/range remembering.

Documentation effects

Add resource provenance and build instructions to README.md; add THIRD_PARTY_NOTICES.md and a CC BY-SA notice beside generated assets; after approval, register this plan in docs/plans/README.md and STATUS.md.

Requirements (confirmed)

User stories

  1. As a reader, I want up to four subtle dictionary cues on the first eligible occurrences in a sitting, so that useful definitions are discoverable without clutter.
  2. As a reader, I want cues only where a normalized visible phrase exactly matches a curated dictionary headword or alias, so that Thread never pretends a guessed connection is authoritative.
  3. As a reader, I want to tap a cued phrase and open its dictionary article directly, so that lookup takes one action.
  4. As a reader, I want tapping the rest of a verse to open a neutral context sheet, so that tapping never silently changes memory state.
  5. As a reader, I want the sheet to show every study note, theme note, and profile whose reference includes the verse—typed and ordered study note exact → study note narrowest → theme → profile—so that local and passage-level explanations are both available.
  6. As a reader, I want related dictionary entries presented as explicit chips, including screen-reader access to inline cues, so that discovery is accessible.
  7. As a reader, I want clear empty states when a verse has no note or related term while remember actions remain available.
  8. As a reader, I want “Remember this verse” to store exactly one one-verse candidate and close with restrained confirmation.
  9. As a reader, I want “Select a passage” to anchor the first verse, instruct me to tap the last verse, preview the normalized range, and require confirmation.
  10. As a reader, I want reverse endpoint taps normalized, cancellation to change nothing, and chapter changes to cancel selection, so that range marking is safe.
  11. As a reader, I want dictionary cue taps disabled during range selection, so that every verse tap has one unambiguous meaning.
  12. As a reader, I want previously remembered verses/ranges to render as remembered and be removable without affecting promoted passages.
  13. As a reader, I want book summaries and full introductions reachable from the context sheet and the Knot, without interrupting Arrival.
  14. As a reader, I want a searchable offline dictionary in the Knot, ranked exact title → title prefix → alias exact/prefix → title substring, so that I can browse beyond the day's text.
  15. As a reader, I want search to be case/diacritic insensitive, debounced, cancellable, and honest about zero results.
  16. As a reader, I want long articles and internal Scripture references readable at large font scale; Scripture links may open the existing Knot chapter view.
  17. As a reader without a network connection, I want notes, dictionary, search, book help, and WEB Scripture to work completely.
  18. As a screen-reader or switch-control user, I want named actions, 44×44 targets, logical focus order, modal focus containment/return, and an alternative list of cued terms.
  19. As a reader using reduced motion, I want sheet/range feedback without essential motion.
  20. As a privacy-conscious reader, I want lookups and searches to stay local and not create analytics events; explicit remembering uses the existing candidate_marked event while unremembering retains its existing local retraction behavior.
  21. As a reader, I want a visible source/licence line on each resource surface and full notices in About, so that provenance is clear.
  22. As the silent lab actor, I want no new arm, seed use, reconciliation rule, or outcome field, so that experiments and year-one/post-day-366 behavior are unchanged.
  23. As a returning reader after a missed day, lapse, or 4 AM boundary, I want resource UI to follow the loaded sitting and never alter scheduling.
  24. As a partner recipient, I want shared cards unchanged and free of embedded Tyndale content, so that partner hand-off and licensing scope do not expand.
  25. As a maintainer, I want deterministic source downloads, parsing, validation, checksums and generated manifests, so that resource updates are reviewable and reproducible.
  26. As a maintainer, I want malformed references/markup to fail the build rather than disappear at runtime.
  27. As a reader on a small phone or tablet, I want the context sheet and library to remain legible without obscuring verse position.

Out of Scope

  • TGC/Crossway Knowing the Bible excerpts; only externally maintained backlinks could be considered separately.
  • Dictionary maps, absent picture art, charts and supplemental textboxes; recognized references to them render an accessible “supplement omitted” marker.
  • Cross-chapter memory selection; the existing PassageRef represents one chapter.
  • Automatic semantic/NLP term linking, full-body dictionary search, personalization, resource history, highlights, annotations, or syncing.
  • Interactive Scripture links inside resource prose in v1; references render as text. Dictionary-to-dictionary links remain interactive inside the resource surface.

Testing Decisions

  • Unit-test the pure XML-to-record transformer with small fixtures, including multi-chapter refs, inline markup, aliases, malformed refs, deterministic output, and licence manifest.
  • Unit-test a public StudyProvider seam for note overlap/order, exact cue matching/caps, search ranking, empty results, and Scripture links. Follow fake-provider patterns in test/text.test.ts and test/dose.test.ts.
  • Extend test/memory.test.ts for confirmed verse ranges and cancellation invariants. Do not unit-test React Native layout snapshots; verify focus, font scale and touch behavior on device.
  • Keep test/backup.test.ts as the proof that static study assets are absent from user backups; add an explicit assertion/comment if the provider ever gains a cache.
