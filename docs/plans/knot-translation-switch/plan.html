Problem & Intent

Status, owner & next action

Status: drafted, awaiting approval. Trigger: the user asked "is it possible in the settings page to switch bible translations?" — answer was no. Designed via /grill (docs/plans/knot-translation-switch/grill-summary.md), confirmed 2026-09-05. Next action: user approval of this plan, then Ticket 1 (see Tickets tab).

Outcome and constraints

Today, translation (NIV / ESV / the bundled WEB floor) is chosen exactly once, at onboarding (src/onboarding/screens/TranslationScreen.tsx). The knot cannot change it, yet DoneScreen.tsx:47 already tells the reader "add a translation any time from the knot" — a promise the code doesn't keep. This plan builds that knot control. It knowingly departs from ../thread-plan_3.html lines 297/313, which call WEB "silent, automatic infrastructure, not a choice" and say it "is never mentioned" — the grill's confirmed reasoning (carried into JOURNAL.md, decision "WEB is a translation you can choose, not silent infrastructure") is that this stance only holds while WEB can only ever appear as an invisible catch; once translation is changeable in the knot, an unnamed fallback plus a bad key produces a reader who believes they're in NIV and isn't. Constraints carried forward: §13.6 hard rules (events append-only, no Math.random(), import boundaries), the on-device-only privacy rule (API keys stay in SQLite meta, never leave the device), and AGENTS.md's verification policy.

Scope and non-goals

In scope: a knot "Translation" section that switches NIV↔ESV↔WEB, validates a licensed key live before saving it, logs the change as a confound, and rebuilds the app's services so it takes effect immediately with today's portion restarting at sitting 1. Also in scope: naming WEB explicitly in onboarding (skip label + DoneScreen copy), and correcting NIV's live-verification status to match ESV's already-honest "unverified" framing, since designing this surfaced that neither provider has ever made a real network call in this codebase (see Evidence). Non-goals: see Requirements tab → Out of Scope.

Dependencies and unresolved gates

One real external dependency: a live api.bible key and a live api.esv.org key (the latter requires accepting Crossway's statement of faith) are both required before merge — the grill session made "both providers pass a live round-trip" an explicit acceptance criterion (round 5, reversing an earlier, unfounded assistant claim that NIV was "already exercised in real use" — see grill-summary.md's Corrections section). No other external gate. No unresolved product decision remains — every open question from the grill's four rounds was answered and confirmed; see Evidence below for the full decision list.

Evidence and decisions

Primary evidence: docs/plans/knot-translation-switch/grill-summary.md (all four rounds) and JOURNAL.md's "WEB is a translation you can choose, not silent infrastructure" decision entry — both written 2026-09-05, both current. Key repository facts this plan relies on, verified directly against this worktree (main @ efcf041, not the stale feat/account-reset checkout the session initially opened — see Consequences below):

  • hasConfound() (src/lab/confound.ts:13) checks only cue_changed and 7+ day gaps today.
  • reconcile() (src/lab/reconcile.ts:24) only ever advances forward from meta['watermark'] — it never replays already-processed past days, so a hasConfound() logic change carries no retroactive risk to already-reported experiment data; only future days can ever contain a translation_changed event.
  • chapter_cache is keyed (translation, book, chapter) — switching translations is safe; each keeps its own rows, no migration needed.
  • events.type is plain TEXT with no CHECK constraint (src/log/schema.ts:14) — adding 'translation_changed' to the EventType union is a TypeScript-only change, not a schema migration.
  • ApiBibleProvider.resolveBibleId() (src/text/apiBible.ts:80-91) caches niv_bible_id in meta globally, not per key — a replaced key without clearing this would inherit a stale bible id.
  • Neither licensed provider has ever made a real network call in this codebase. src/text/esv.ts:11 says so explicitly ("UNVERIFIED AGAINST A LIVE KEY"); apiBible.ts says nothing, so it reads as proven by omission — but every NIV test mocks fetchFn (test/text.test.ts:141,164) and the file's only claim is that the base host matched published docs (apiBible.ts:13), not a live call. An earlier version of that file used the wrong host and "would fail silently into the WEB fallback forever" (apiBible.ts:14) — the exact failure mode this feature exists to make visible, and it already happened here once, undetected.
  • services is rebuilt via useMemo(() => createServices(db), [db, onboarded]) (App.tsx:28) today, already precedent for fully recreating every service (log, cue, memory, notifier, backup, partner, text) on a dependency change — this plan reuses that exact mechanism rather than inventing a new one.
  • Flow.tsx:66-68's useEffect(() => { void session.load(db, log, text, today); }, [db, log, text, today]) already re-fires whenever text's object identity changes — so bumping App.tsx's services-rebuild epoch is sufficient to reload today's portion; no change to Flow.tsx or the useSession store is needed.
  • session.load() (src/state/session.ts:89) reads current_sitting fresh from meta on every call and clamps to it — so writing meta['current_sitting'] = '0' at the moment of switching, before the reload fires, is sufficient to "restart at sitting 1" with no change to session.ts itself.
  • Smart Review finding (integrated): App.tsx's boot-sequence effect (App.tsx:30-53) depends on [onboarded, services, db] — the whole services object, not a narrower slice. A first implementation draft that bumped serviceEpoch to change services's identity would therefore re-fire this effect on every translation switch, not just app launch, appending a spurious app_open event (§13.6 append-only — a permanent, wrong record) and re-running reconcile()/maybeGenerateReports(). The fix (see Implementation tab) reads services through a ref inside that effect instead of depending on it directly, so it still fires exactly once per real onboarding-complete/launch transition and never on a translation switch.

Design tokens: no new token needed. Reuses tokens.color.{ink,ink15,ink40,thread,dyeSoft,paper} and tokens.font.display exactly as src/knot/BackupSection.tsx and src/onboarding/screens/TranslationScreen.tsx already use them (see Aesthetics tab).

Requirements (confirmed)

User stories

  1. As a reader who chose NIV or ESV at onboarding, I want to switch to the other licensed translation from the knot, so that I can change my mind without resetting the app.
  2. As a reader currently on WEB (skipped onboarding's translation step), I want to add a licensed translation from the knot, so that DoneScreen's existing promise is actually true.
  3. As a reader on a licensed translation, I want to deliberately switch to the World English Bible, so that I have an explicit, named way back to the offline text rather than only an implicit silent fallback.
  4. As a reader pasting a new or replacement API key, I want the knot to prove the key works before saving it, so that a typo or a revoked key never leaves me silently reading WEB while believing I'm reading NIV/ESV.
  5. As a reader switching back to a translation I've used before, I want my previously entered key pre-filled, so that I don't have to dig it out and retype it.
  6. As a reader whose key fails validation, I want a clear on-screen error and my current translation left untouched, so that a failed attempt never silently degrades what I'm already reading.
  7. As a reader mid-way through an unsealed multi-sitting chapter who switches translation, I want today's portion to reload and restart at the first sitting, so that I never silently skip verses the old sitting split hadn't shown me yet.
  8. As a reader who has already sealed today, I want switching translation to have no visible effect on today's completed reading, so that changing my mind about translation never threatens an already-sealed streak day.
  9. As the lab, I want a translation change logged as its own event and treated as a confound exactly like a cue change, so that days around a switch are reported but excluded from experiment verdicts, per §19.
  10. As the reader, I want onboarding to name the World English Bible explicitly wherever it offers it (the skip path, the done screen), so the same translation isn't unnamed in one place and named in another.
  11. As an existing installed reader with a translation already configured before this feature shipped, I want my existing API key to keep working after the app updates, so upgrading doesn't silently revert me to WEB.
  12. As a maintainer, I want NIV's live-untested status made as visible as ESV's already is, so a future reader doesn't wrongly infer NIV is proven just because nobody documented otherwise.
  13. As a reader, I want choosing WEB to require no network call and no key, so reverting to the offline text always works exactly like it does today, even fully offline.
  14. As a reader with no connectivity attempting to add or switch to a licensed provider, I want the validation round-trip to fail clearly — not hang, not silently fall back — so I understand why the switch didn't take effect.

Out of Scope

  • Detecting or surfacing an in-progress silent WEB fallback — e.g. a working key that goes offline later, after a successful switch. Validate-before-save only proves the key at the moment of saving; ongoing fallback detection is unchanged existing ChainedProvider behavior and was never decided in the grill.
  • Multi-translation side-by-side reading — explicitly cut by thread-plan_3.html:226.
  • Any partner-facing behavior — the partner hand-off has no relationship to translation choice.
  • Re-litigating onboarding's screen order, or adding a third onboarding card for WEB — round 4 of the grill explicitly kept the skip path as the only WEB route in onboarding.
  • Retroactively re-splitting or backfilling already-sealed days — sealed history (chapter_cache, passages, events) is immutable; only today's unsealed portion reloads.
  • Encrypting or otherwise hardening backup exposure of the now-two API keys living in meta — a pre-existing, slightly widened exposure flagged in the grill's Open Threads; backup encryption is an existing opt-in toggle (BackupSection.tsx) untouched by this plan.

  const cueChanged = events.some((e) => e.type === 'cue_changed');
  const translationChanged = events.some((e) => e.type === 'translation_changed');
  return cueChanged || translationChanged || gapDays >= 7;
}

/**
 * Cache-free live check that an ESV key actually authenticates — the
 * ESV equivalent of resolveNivBibleId's role for NIV (apiBible.ts).
 * Deliberately does NOT go through EsvProvider.getChapter(): that
 * method checks chapter_cache first, so a previously-cached chapter
 * would let a revoked or rotated key "pass" validation with no live
 * network call at all — exactly the silent-fallback failure this
 * whole feature exists to prevent (docs/plans/knot-translation-switch).
 */
export async function probeEsvKey(apiKey: string, fetchFn: typeof fetch = fetch): Promise {
  const params = new URLSearchParams({
    q: 'John 1:1',
    'include-verse-numbers': 'false',
    'include-footnotes': 'false',
    'include-footnote-body': 'false',
    'include-headings': 'false',
    'include-passage-references': 'false',
    'include-short-copyright': 'false',
    'include-copyright': 'false',
  });
  const res = await fetchFn(`https://api.esv.org/v3/passage/text/?${params}`, {
    headers: { Authorization: `Token ${apiKey}` },
  });
  if (!res.ok) throw new Error(`ESV API ${res.status} — check the key`);
  const body = (await res.json()) as { passages?: string[] };
  if (!body.passages?.[0]) throw new Error('ESV API returned no passage — check the key');
}

src/text/translationService.ts — NEW🟡 high-effort — owns the confound-logging decision and the meta key scheme this whole feature depends on
import type { SqlDb } from '../log/db';
import type { Log } from '../log/log';
import { meta } from '../log/log';
import { resolveNivBibleId } from './apiBible';
import { probeEsvKey } from './esv';

export type Provider = 'niv' | 'esv';

export interface ValidatedKey {
  /** Only set for NIV — the resolved bible id, ready to cache immediately. */
  nivBibleId?: string;
}

/**
 * §04/§19 knot control — owns the reader's translation choice the same
 * way CueService (src/cue/index.ts) owns the cue: reads/writes meta,
 * and is the one place that decides when a translation_changed
 * confound (§13) is logged. validate() never touches chapter_cache —
 * a cached chapter would let a revoked/rotated key "pass" with no live
 * network call at all, defeating the point of validating before save
 * (docs/plans/knot-translation-switch).
 */
export class TranslationService {
  constructor(
    private readonly db: SqlDb,
    private readonly log: Log,
  ) {}

  /** Normalizes meta's raw string (absent key, or '' meaning "cleared" — same idiom as next_book in session.ts) to null. */
  current(): Provider | null {
    const raw = meta.get(this.db, 'text_provider');
    return raw === 'niv' || raw === 'esv' ? raw : null;
  }

  /** The stored key for a provider, so the knot can pre-fill it on re-selection rather than asking the reader to retype it. */
  keyFor(provider: Provider): string | null {
    return meta.get(this.db, `text_provider_key_${provider}`) || null;
  }

  /**
   * Live round-trip proving the key actually authenticates, before
   * anything is saved. Throws with a message fit to show the reader.
   */
  async validate(provider: Provider, apiKey: string, fetchFn: typeof fetch = fetch): Promise {
    if (provider === 'niv') return { nivBibleId: await resolveNivBibleId(apiKey, fetchFn) };
    await probeEsvKey(apiKey, fetchFn);
    return {};
  }

  /**
   * Persists an already-validated provider + key as the active
   * translation. Never call this without a preceding validate() —
   * same division of responsibility BackupSection already uses for
   * its passphrase form (validate, then save; never the reverse).
   */
  set(provider: Provider, apiKey: string, validated: ValidatedKey): void {
    const previous = this.current();
    meta.set(this.db, `text_provider_key_${provider}`, apiKey);
    meta.set(this.db, 'text_provider', provider);
    // A replaced NIV key can resolve to a different bible id — cache
    // the id validate() just resolved, so ApiBibleProvider never reads
    // a stale one left over from the previous key (apiBible.ts:80-91).
    if (provider === 'niv') meta.set(this.db, 'niv_bible_id', validated.nivBibleId ?? '');
    // Restart today's portion at sitting 1 rather than clamping into
    // it — session.load() (src/state/session.ts) reads this fresh, and
    // sittings are derived from per-translation verse counts, so
    // clamping into whatever index the OLD translation left behind can
    // skip verses the reader never saw. Re-reading is the safe
    // failure; skipping is not.
    meta.set(this.db, 'current_sitting', '0');
    if (previous !== provider) this.log.write({ type: 'translation_changed' });
  }

  /** No key, no round-trip — WEB is always present, offline, by construction. */
  setOffline(): void {
    const previous = this.current();
    meta.set(this.db, 'text_provider', '');
    meta.set(this.db, 'current_sitting', '0');
    if (previous !== null) this.log.write({ type: 'translation_changed' });
  }
}

/**
 * One-time carry-forward for an install that chose a translation
 * before this file existed: the single legacy `text_provider_key`
 * meta row becomes `text_provider_key_<provider>`, so an existing
 * reader's key survives the upgrade instead of silently reverting to
 * WEB. Additive and idempotent — safe to call on every app open.
 *
 * Always clears the legacy row once it has been read, whether or not
 * a copy actually happened — a stale, possibly-revoked copy must not
 * survive indefinitely in `meta` (and every future unencrypted backup)
 * once it's superseded. (Smart Review MEDIUM: the original draft never
 * cleared it, and OnboardingFlow.tsx still wrote to the legacy row on
 * every fresh install, not just pre-existing ones — both are fixed:
 * this function now clears the legacy row, and OnboardingFlow.tsx
 * below writes the per-provider key directly, so the legacy row is
 * only ever populated by a genuinely pre-upgrade install.)
 */
export function migrateLegacyProviderKey(db: SqlDb): void {
  const provider = meta.get(db, 'text_provider');
  const legacy = meta.get(db, 'text_provider_key');
  if (!legacy) return; // nothing to migrate — fresh per-provider install, or already migrated+cleared
  if (provider === 'niv' || provider === 'esv') {
    const perProviderKey = `text_provider_key_${provider}`;
    if (!meta.get(db, perProviderKey)) meta.set(db, perProviderKey, legacy);
  }
  meta.set(db, 'text_provider_key', ''); // clear — must not survive as an orphaned copy
}

describe('TranslationService', () => {
  it('current() is null when nothing is set, and after setOffline()', () => {
    const { translation } = setup();
    expect(translation.current()).toBeNull();
    translation.setOffline();
    expect(translation.current()).toBeNull();
  });

  it('set() persists the provider and per-provider key, and keyFor() reads it back', async () => {
    const { db, translation } = setup();
    const fetchFn = (async () => ({ ok: true, json: async () => ({ data: [{ id: 'niv-uuid', abbreviation: 'NIV' }] }) })) as unknown as typeof fetch;
    const validated = await translation.validate('niv', 'key-a', fetchFn);
    translation.set('niv', 'key-a', validated);
    expect(translation.current()).toBe('niv');
    expect(translation.keyFor('niv')).toBe('key-a');
    expect(meta.get(db, 'niv_bible_id')).toBe('niv-uuid');
  });

  it('switching providers keeps the old provider\'s key retrievable', async () => {

    translation.set('niv', 'niv-key', await translation.validate('niv', 'niv-key', nivFetch));

HIGH — 1 finding, fixed

App.tsx's reconcile/app_open boot effect would re-fire on every translation switch. The original draft added serviceEpoch to the services useMemo without noticing the boot effect's own dependency array is [onboarded, services, db] — the whole object, not a narrower slice. Since a translation switch bumps serviceEpoch, which changes services's identity through that same memo, every switch would re-run reconcile(), re-run maybeGenerateReports(), and unconditionally write a fresh { type: 'app_open' } row to the append-only events log for something that is not a launch. reconcile()/ maybeGenerateReports()/autoExportIfDue() are idempotent, so those parts were merely wasteful — but the spurious app_open write is a permanent, wrong record in the log this project treats as source of truth. Fix (Implementation tab, App.tsx): the boot effect now reads log/backup through a servicesRef instead of depending on services directly, keeping its trigger set at [onboarded, db] — its original, correct scope — so it still fires exactly once per real launch and never on a translation switch.

MEDIUM — 1 finding, fixed

The legacy single API key was never cleared, and onboarding kept writing it forever — not just for pre-existing installs. The original draft left OnboardingFlow.tsx:44 writing to the old singular text_provider_key meta row unchanged, which meant migrateLegacyProviderKey() was doing double duty as the only bridge for every fresh onboarding completion, not a true legacy-only path — and it never deleted the row it copied from, so a superseded (possibly rotated or revoked) key would sit in meta, and in every future unencrypted backup, forever. Fix (Implementation tab): OnboardingFlow.tsx now writes directly to text_provider_key_<provider>, so the legacy row is only ever populated by a genuinely pre-upgrade install; migrateLegacyProviderKey() now unconditionally clears the legacy row once read, whether or not a copy happened.
